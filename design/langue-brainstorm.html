01-why.langue

왜 다시 만드는가

레거시 컴파일러에서 문법만이 유일하게 선언적이었고(lumo.langue), 동시에 가장 고치기 즐거운 부분이었다. CST 이후의 모든 것 — HIR 로워링, 스코핑, 타입 검사 — 은 손으로 쓴 Rust였고, 언어의 정의는 그 코드들의 안무 속에 암묵적으로 흩어져 있었다.

① LIR rewrite→ ② typecheck→ ③ patch type_args→ ④ resolve defaults→ ⑤ re-typecheck

레거시 — 정의가 코드 안에

각 페이즈가 앞 페이즈의 상태를 덧대어 고치는 5단계 안무. 규칙 하나를 바꾸려면 어느 페이즈가 어떤 상태를 만지는지 전부 기억해야 했다. 비어 있던 lumo2hir.langue 플레이스홀더가 증언하듯, 번역까지 선언적으로 쓰고 싶다는 욕구는 이미 있었다.

Langue 2 — 정의가 파일 안에

토큰부터 타입 판단까지 하나의 정의 아티팩트. Rust는 정의를 실행하는 엔진과 생성된 코드일 뿐이며, 선언으로 못 쓰는 부분은 extern으로 이름을 밝히고 뚫는다 — grep extern 한 번이면 선언적 이야기의 구멍이 전부 보인다.

02-project.langue

프로젝트 형식 — 기능 단위로 썰어 담는다

언어 정의는 여러 파일로 이루어진 Langue 프로젝트다. 파일은 종류 접미사로 역할이 정해지고, 명시적 use import로 연결된다. 덕분에 정의를 단계별 한 덩어리가 아니라 기능(fn, cap, data, pattern…) 단위로 썰 수 있다.

  • 도달성 검사 — 루트에서 import로 닿지 않는 .langue 파일은 조용히 무시되지 않고 langc check 에러다.
  • import 형태 — use "./a.syn.langue"(전부) · as core(한정) · (Expr, BinExpr)(선택). 상대 경로, 비전이적, v1에서 순환 금지.
  • 가산적 병합 — 같은 종류의 파일들은 하나의 정의로 합쳐진다. fn.type.langue과 cap.type.langue이 같은 infer/check에 규칙을 보태고, 전체 병합 후 망라성·중복을 전역 검사.
03-pipeline.langue

파이프라인 모양은 Langue가 정하지 않는다

결정 사항: 정의는 임의 개수의 트리를 선언하고 그 사이를 elab으로 잇는다. 표면 트리는 .syn.langue에서 나오고, 나머지는 전부 .tree.langue의 선택이다. HIR/LIR이 몇 단계인지, CBPV를 두 트리로 쪼갤지는 Lumo 정의 안에서 내리는 결정이지 도구의 제약이 아니다.

04-kinds.langue

다섯 가지 파일 종류

접미사가 곧 역할이다. 아래 코드는 전부 design/langue.md의 실제 스케치.

*.syn.langue어휘 + CST 문법
langue 1의 계승. 최대 함정이었던 래퍼 노드 관례는 sep() 내장으로, 손으로 짜던 Pratt 파서는 우선순위 주석으로 흡수한다.
token Ident = /[a-zA-Z_][a-zA-Z0-9_]*/
        keywords('fn' 'data' 'cap' …)

FnDecl = 'fn' name:Ident params:sep(Param, ',') …
Expr   = infix BinExpr {
  '|>' left, '+' '-' left @ 60, '*' '/' left @ 70
}
*.tree.langue트리 선언
탈설탕 이후의 트리들을 평범한 ADT로 선언. Rust enum·프리티 프린터· 패턴 매칭 표면이 생성된다.
tree Core {
  Expr {
    Lam(param: Binder, body: Expr)
    App(callee: Expr, arg: Expr)
    Perform(cap: CapRef, args: List(Expr))
  }
}
*.elab.langue정제: 트리 → 트리 규칙
소스 쪽은 준인용 패턴, 타깃 쪽은 생성자. 노드 종류당 하나의 규칙, 문법에 대해 망라성 검사. 재귀는 elab(…)으로 명시적.
elab Surface -> Core {
  rule FnDecl { name, params, body } =>
    Let(name, foldr(params, elab(body),
                    |p, acc| Lam(p, acc)))
  rule PipeExpr { lhs, rhs } =>   // a |> f ⇒ f(a)
    App(elab(rhs), elab(lhs))
}
*.scope.langue바인딩 구조
스코프 그래프식 사실 선언(Statix에서 영감, 훨씬 작게). 엔진이 CST 한 번 순회로 그래프를 만들고, LSP의 go-to-def가 공짜로 따라온다.
FnDecl  declares name in enclosing  // letrec
Param   declares name in body
LetExpr declares binder in body    // 섀도잉
Ident   resolves in lexical scope
*.type.langue타입 판단 — 가장 야심차고, 가장 절제된 부분
System Fω 카인드, spine-local 양방향 추론, capability row는 엔진 원시 연산이라 정의할 수 없고 호출만 가능하다. DSL이 소유하는 것: 어떤 노드에 어떤 규칙이 발화하는지, 전제가 무엇인지, 실패 시 어떤 진단을 내는지. 표현 불가능한 규칙은 extern rule로 이름만 남기고 Rust로.
rule infer App(f, a):
  infer(f) ~> Fn(param, ret | caps)
    else error "cannot call a non-function of type {0}" at f
  check(a, param)
    else error "expected {param}, found {0}" at a
  -----------------------------------
  ret | caps
05-exec.langue

실행 모델 — 생성과 해석의 하이브리드 (제안, 반론 환영)

crates/langc 하나가 라이브러리(컴파일러에 정의를 탑재) + CLI (langc gen, langc check)를 겸한다.

생성되는 것

syn · tree → Rust 소스 코드
  • 토큰 DFA, SyntaxKind, 무손실 트리
  • 타입이 붙은 AST 접근자
  • 표면 파서 (우선순위 주석 + extern 복구 훅)
  • 트리 enum과 프리티 프린터

이유: 형태를 정하는 뜨거운 경로. 레거시 langue와 같은 워크플로 — 수정, langc gen, 커밋.

해석되는 것

elab · scope · type → 검증된 규칙 테이블
  • elab 재작성 규칙
  • 스코프 사실과 해석 질의
  • 타입 판단 규칙 + 진단 템플릿

이유: 타입 규칙 하나 고치자고 생성된 Rust를 재컴파일하지 않기. 의미는 조밀하지만 v1에서 코드젠이 필요할 만큼 성능 임계는 아니다 — 프로파일이 반박하면 그때 생성으로.

06-typing.langue

규칙 옆에 사는 에러 메시지

결정 사항: 진단 템플릿은 DSL 안에 산다. 전제마다 else error "…" at 노드를 달 수 있고, 엔진이 타입·이름 구멍을 채우고 at을 스팬으로 옮긴다. 에러 품질이 정의 파일에서 리뷰 가능해진다.

Γ ⊢ f ⇒ Fn(π, ρ | ε) Γ ⊢ a ⇐ π Γ ⊢ f(a) ⇒ ρ | ε
else error "cannot call a non-function of type {0}" at f
else error "expected {param}, found {0}" at a

전제 위에 마우스를 올리면 그 전제가 실패했을 때의 진단이 표시됩니다

  • 엔진 원시 연산(호출만 가능): 단일화 ~>, 인스턴스화/일반화, 카인드 검사, capability row 연산, 신선한 메타변수.
  • DSL 소유: 규칙의 발화 대상 노드, 전제 목록, 전제별 진단. spine-local 양방향(⇒ 추론 / ⇐ 검사)은 판단의 모드로 노출.

08-milestones.langue

마일스톤

각 단계에서 langc check와 golden 테스트를 초록으로 유지. 레거시 legacy/crates/compiler/tests/fixtures/가 승계 계약이다.

  1. M0

    langc 코어

    .langue 파서, 프로젝트/import 모델, langc check. Lumo의 .syn.langue 이식 — 레거시 langue가 생성하던 것(SyntaxKind, AST, 무손실 트리)에 더해 표면 파서까지 생성.

  2. M1

    tree + elab

    Core 트리 선언, Surface → Core 규칙 작성. 재작성 엔진이 수기 HIR 로워링을 대체. CBPV 분리 여부를 여기서 결정.

  3. M2

    scope

    스코프 사실 + 해석 엔진. LSP go-to-def의 기반.

  4. M3

    type

    판단 DSL + Fω/capability 원시 연산을 가진 양방향 엔진. capability 타입 규칙 이식.

  5. M4

    재연결

    백엔드(레거시 ts.rs/rs.rs의 지식으로 Core 위에 새로 작성), 테스트 픽스처 이식.
