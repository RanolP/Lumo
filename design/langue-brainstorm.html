01-why.langue

왜 다시 만드는가

레거시 컴파일러에서 문법만이 유일하게 선언적이었고(lumo.langue), 동시에 가장 고치기 즐거운 부분이었다. CST 이후의 모든 것 — HIR 로워링, 스코핑, 타입 검사 — 은 손으로 쓴 Rust였고, 언어의 정의는 그 코드들의 안무 속에 암묵적으로 흩어져 있었다.

① LIR rewrite→ ② typecheck→ ③ patch type_args→ ④ resolve defaults→ ⑤ re-typecheck

레거시 — 정의가 코드 안에

각 페이즈가 앞 페이즈의 상태를 덧대어 고치는 5단계 안무. 규칙 하나를 바꾸려면 어느 페이즈가 어떤 상태를 만지는지 전부 기억해야 했다. 비어 있던 lumo2hir.langue 플레이스홀더가 증언하듯, 번역까지 선언적으로 쓰고 싶다는 욕구는 이미 있었다.

Langue 2 — 정의가 파일 안에

토큰부터 타입 판단까지 하나의 정의 아티팩트. Rust는 정의를 실행하는 엔진과 생성된 코드일 뿐이며, 선언으로 못 쓰는 부분은 extern으로 이름을 밝히고 뚫는다 — grep extern 한 번이면 선언적 이야기의 구멍이 전부 보인다.

02a · 결정됨 — 이전의 미결 문항을 닫는다

salsa식 증분 질의, 첫날부터

모든 파생 산출물은 입력에 대한 메모이즈된 질의다. 편집이 더럽힌 것만 다시 계산한다. cat/병합/DCE가 만드는 정의는 리비전당 하나의 불변 값 — 메모이제이션이 원하는 바로 그 형태다. 두 층이 같은 질의 런타임 위에 선다.

정의 층 (langc) · parse(file)→ merged_definition→ rule_tables(kind)→ 생성 코드
컴파일 층 (생성된 컴파일러) · cst(file)→ tree(file, "Core")→ resolve(node)→ infer(node)

.type.langue 파일 하나를 고치면 타입 테이블만 재파생된다. 후보 런타임: salsa 크레이트, 혹은 추론 엔진과 충돌하면 목적 제작.

02b · langue 1의 혈통

ungrammar식 표기 — 모양을 쓰면, 알고리즘은 유도된다

.langue 표기는 트리의 모양을 기술하지, 파싱 알고리즘을 기술하지 않는다. 레이블은 접근자가 되고, 대안은 노드 종류가 되고, 파서는 모양(+ 우선순위 주석)에서 유도된다. 별도의 ADT 표기는 없다 — 모든 트리는 문법으로 선언되고, 따라서 자기 표시 문법을 가진다. 표면이든 내부(Core 등)든 파서와 프리티 프린터가 함께 유도되어 모든 단계가 텍스트로 왕복한다. 이 철학이 문법 너머까지 간다: elab 규칙·스코프 사실·타입 규칙 전부가 엔진이 해석하는 모양-우선·알고리즘-부재 선언이다.

// 무엇을 쓰는가: 트리의 모양 = 곧 그 트리의 표시 문법
FnDecl = 'fn' name:Ident params:sep(Param, ',') …
// 무엇을 쓰지 않는가: peek() / expect() / 재귀 하강의 순서 / print 함수
02c · 결정됨

e-graph 정제 — 최적화는 등식 포화로

정제는 기계가 다른 두 모드로 갈린다.

트리 → 다른 트리: 구문 지향

elab Surface -> Core는 결정적 단일 패스 번역. 노드 종류당 규칙 하나, 망라성 검사. 의미의 정의이므로 탐색할 것이 없다.

같은 트리: 등식 포화

elab Core -> Core 규칙군은 e-graph 위의 비파괴 재작성. 포화까지 돌리므로 규칙 순서가 무의미 — 파일 순서가 무의미한 cat과 같은 원리다. 레거시 LTO(인라이닝·CPS 제거·DCE)가 손으로 배열한 패스 대신 선언된 등식으로 부활한다.

비용과 추출

포화 후 e-class마다 비용 모델로 최적 대표를 추출. 비용을 어디에 선언하나(생성자 주석 / 규칙 가중치 / extern)는 미결.

02d · 결정됨

플러그형 타입 시스템 — 제대로 된 추론 엔진 위에서

추론 엔진

추론 규칙 해석기. 진짜 유도 트리를 만든다. 전제, 모드(⇒/⇐), 단일화, 인스턴스화, 신선한 메타변수가 엔진 서비스. 엔진은 Lumo를 모른다.

타입 시스템 = 플러그인

Rust 쪽 원시 연산 묶음(타입 형성자·카인드 규칙·row 연산) + DSL 규칙 집합. Lumo v1은 Fω + spine-local 양방향 + capability row를 꽂는다. 엔진을 안 건드리고 다른 시스템으로 교체 가능.

유도가 곧 산출물

실패한 전제 → 진단 템플릿. 성공한 유도 → "왜 이 타입인가" 설명과 LSP 호버. 모든 유도는 salsa 질의라 증분 재검사가 공짜로 따라온다.

Γ ⊢ f ⇒ Fn(π, ρ | ε) Γ ⊢ a ⇐ π Γ ⊢ f(a) ⇒ ρ | ε
else error "cannot call a non-function of type {0}" at f
else error "expected {param}, found {0}" at a

전제 위에 마우스를 올리면 그 전제가 실패했을 때의 진단이 표시됩니다 — 진단 템플릿은 규칙 옆, DSL 안에 산다 (결정됨)

03-project.langue

프로젝트 형식 — import 없이, cat으로

언어 정의는 여러 파일로 이루어진 Langue 프로젝트지만 import는 없다. 프로젝트의 모든 .langue 파일이 stdlib과 함께 그대로 연결(cat)되어 하나의 전역 이름공간이 된다. 파일은 종류 접미사로 역할만 정해지므로, 배선 의식 없이 정의를 기능(fn, cap, data, pattern…) 단위로 썰 수 있다.

03a · project-wide cat

langc가 루트 아래 모든 종류 접미사 파일을 모아 하나의 정의로 병합. 파일 순서도 항목 순서도 무의미하고, 전방 선언 없이 모든 항목이 서로를 본다 (파일과 stdlib을 가로지르는 letrec식 전역 스코프).

03b · stdlib 포함

foldr/map 같은 도우미, 표준 토큰 클래스, List 같은 기본 형태가 프로젝트 파일과 같은 이름공간에 참여한다 — stdlib 파일이 cat에 끼어 있는 것과 정확히 같다.

03c · 도달성 에러 대신 DCE

안 쓰인 항목은 정의 로드 시 제거된다. "import해야 유효"라는 개념 자체가 없다. 프로젝트 항목의 미사용은 선택적 린트로만 노출.

03d · 충돌과 가산 병합

같은 이름 두 개는 에러. 설계된 예외는 가산 병합 — fn.type.langue과 cap.type.langue이 같은 infer/check에 규칙을 보태고, 병합 후 망라성·중복을 전역 검사.

04-syntax.langue

문법 — 모양을 쓰면 파서와 프린터가 나온다

표면 언어든 내부 트리든 전부 .syn.langue다. 문법이 노드의 모양과 표시 문법을 동시에 정하고, 파서·프리티 프린터가 트리마다 유도된다. 트리를 몇 단계 둘지, CBPV를 두 트리로 쪼갤지는 Lumo 정의 안에서 내리는 결정이지 도구의 제약이 아니다.

*.syn.langue04a · 표면: 어휘 + CST 문법
langue 1의 계승. 최대 함정이었던 래퍼 노드 관례는 sep() 내장으로, 손으로 짜던 Pratt 파서는 우선순위 주석으로 흡수한다.
token Ident = /[a-zA-Z_][a-zA-Z0-9_]*/
        keywords('fn' 'data' 'cap' …)

FnDecl = 'fn' name:Ident params:sep(Param, ',') …
Expr   = infix BinExpr {
  '|>' left, '+' '-' left @ 60, '*' '/' left @ 70
}
*.syn.langue04b · 내부 트리 — tree kind는 없다
탈설탕 이후의 트리도 ADT가 아니라 문법으로 선언한다 (tree Core로 스코프). 파서와 프리티 프린터가 함께 유도되어 모든 단계가 텍스트로 왕복 — 레거시 hir.langue/lir.langue 방식의 공식화. 디버그 덤프, --emit core, IR 문법으로 직접 쓰는 golden 픽스처가 공짜.
// core.syn.langue
tree Core

Expr = | Lam | App | Let | Perform
Lam  = 'fn' param:Binder '->' body:Expr
App  = callee:Expr '(' arg:Expr ')'
05-scope.langue

스코프 — 바인딩은 사실의 나열이다

스코프 그래프식 사실 선언(Statix에서 영감, 훨씬 작게). 엔진이 CST 한 번 순회로 그래프를 만들고 해석 질의에 답한다. 결과는 타입 검사(07)와 LSP 양쪽에 먹인다 — go-to-def가 공짜로 따라온다.

*.scope.langue선언 · 참조 · 가시성
FnDecl  declares name in enclosing  // letrec — 모듈 전역 가시
Param   declares name in body
LetExpr declares binder in body    // 순차적, 섀도잉
MatchArm declares pattern_binders in body
Ident   resolves in lexical scope
06-elab.langue

정제 — 의미는 규칙으로, 최적화는 등식으로

소스 쪽은 준인용 패턴, 타깃 쪽은 생성자. 트리 간 로워링은 노드 종류당 규칙 하나에 망라성 검사, 재귀는 elab(…)으로 명시적. 같은 트리 규칙군은 e-graph 등식 포화로 돈다(02c). 도우미(foldr, map, 신선한 이름)는 stdlib에서.

*.elab.langue트리 → 트리 · 트리 → 같은 트리
elab Surface -> Core {
  rule FnDecl { name, params, body } =>
    Let(name, foldr(params, elab(body), |p, acc| Lam(p, acc)))
  rule PipeExpr { lhs, rhs } =>   // a |> f ⇒ f(a)
    App(elab(rhs), elab(lhs))
}
07-type.langue

타입 — 가장 야심차고, 가장 절제된 부분

추론 엔진(02d)이 유도를 만들고, 플러그인(Lumo v1: Fω + spine-local 양방향 + capability row)이 원시 연산을 제공한다 — DSL에선 정의할 수 없고 호출만 가능. DSL이 소유하는 것: 어떤 노드에 어떤 규칙이 발화하는지, 전제가 무엇인지, 실패 시 어떤 진단을 내는지(템플릿은 규칙 옆에). 표현 불가능한 규칙은 extern rule로 이름만 남기고 Rust로.

*.type.langue판단 · 규칙 · 진단 템플릿
rule infer App(f, a):
  infer(f) ~> Fn(param, ret | caps)
    else error "cannot call a non-function of type {0}" at f
  check(a, param)
    else error "expected {param}, found {0}" at a
  -----------------------------------
  ret | caps
08-exec.langue

실행 모델 — 생성과 해석의 하이브리드 (제안, 반론 환영)

crates/langc 하나가 라이브러리(컴파일러에 정의를 탑재) + CLI (langc gen, langc check)를 겸한다.

생성되는 것

syn → Rust 소스 코드 (선언된 트리마다)
  • 토큰 DFA, SyntaxKind, 무손실 트리
  • 타입이 붙은 AST 접근자
  • 각 트리의 파서 (우선순위 주석 + extern 복구 훅)
  • 각 트리의 프리티 프린터 — 텍스트 왕복

이유: 형태를 정하는 뜨거운 경로. 레거시 langue와 같은 워크플로 — 수정, langc gen, 커밋.

해석되는 것

elab · scope · type → 검증된 규칙 테이블
  • elab 재작성 규칙 → e-graph 엔진 (02c)
  • 스코프 사실과 해석 질의 → 스코프 그래프 엔진
  • 타입 판단 규칙 + 진단 템플릿 → 추론 엔진 (02d)

이유: 타입 규칙 하나 고치자고 생성된 Rust를 재컴파일하지 않기. 의미는 조밀하지만 v1에서 코드젠이 필요할 만큼 성능 임계는 아니다 — 프로파일이 반박하면 그때 생성으로.

10-milestones.langue

마일스톤

각 단계에서 langc check와 golden 테스트를 초록으로 유지. 레거시 legacy/crates/compiler/tests/fixtures/가 승계 계약이다.

  1. M0

    langc 코어

    .langue 파서, 프로젝트 cat/병합/DCE 모델, langc check, salsa 질의 런타임 뼈대. Lumo의 .syn.langue 이식 — 레거시 langue가 생성하던 것(SyntaxKind, AST, 무손실 트리)에 더해 표면 파서까지 생성.

  2. M1

    내부 트리 + elab (로워링)

    core.syn.langue 작성(Core의 모양 + 표시 문법), Surface → Core 구문 지향 규칙 작성. 재작성 엔진이 수기 HIR 로워링을 대체. CBPV 분리 여부를 여기서 결정.

  3. M2

    scope

    스코프 사실 + 해석 엔진. LSP go-to-def의 기반.

  4. M3

    type

    추론 엔진 + Fω/capability 플러그인 + 판단 DSL. capability 타입 규칙 이식.

  5. M4

    e-graph 최적화

    같은 트리 elab 규칙군을 등식 포화로. 레거시 LTO 픽스처가 계약.

  6. M5

    재연결

    백엔드(레거시 ts.rs/rs.rs의 지식으로 Core 위에 새로 작성), 남은 테스트 픽스처 이식.
