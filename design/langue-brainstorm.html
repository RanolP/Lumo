01-project.langue

프로젝트 형식 — import 없이, cat으로

언어 정의는 여러 파일로 이루어진 Langue 프로젝트지만 import는 없다. 프로젝트의 모든 .langue 파일이 stdlib과 함께 그대로 연결(cat)되어 하나의 전역 이름공간이 된다. 파일은 종류 접미사로 역할만 정해지므로, 배선 의식 없이 정의를 기능(fn, cap, data, pattern…) 단위로 썰 수 있다.

01a · project-wide cat

langc가 루트 아래 모든 종류 접미사 파일을 모아 하나의 정의로 병합. 파일 순서도 항목 순서도 무의미하고, 전방 선언 없이 모든 항목이 서로를 본다 (파일과 stdlib을 가로지르는 순서 무관 전역 스코프).

01b · stdlib 포함

foldr/map 같은 도우미, 표준 토큰 클래스, List 같은 기본 형태가 프로젝트 파일과 같은 이름공간에 참여한다 — stdlib 파일이 cat에 끼어 있는 것과 정확히 같다.

01c · 도달성 에러 대신 DCE

안 쓰인 항목은 정의 로드 시 제거된다. "import해야 유효"라는 개념 자체가 없다. 프로젝트 항목의 미사용은 선택적 린트로만 노출.

01d · 충돌과 가산 병합

같은 이름 두 개는 에러. 설계된 예외는 가산 병합 — fn.type.langue과 cap.type.langue이 같은 infer/check에 규칙을 보태고, 병합 후 망라성·중복을 전역 검사.

02-syntax.langue

*.syn.langue는 언어를 선언한다

Lumo, MIR, LIR, JS 등 다양한 언어를 선언할 수 있으며, 구성 요소로는 토큰과 문법이 있다. 파일 이름이 곧 선언 — MIR.syn.langue가 있으면 이름 MIR가 스코프에 올라 언어로써 참조된다. 여러 파일로 쪼갤 땐 Lumo.expr.syn.langue처럼 첫 조각이 언어. 무손실(trivia 보존) 여부는 언어별로 정의한다.

토큰02a · 이름 = 리터럴 또는 정규식
이름이 곧 디버그·진단 표시. 점 이름은 하이라이트 스코프 겸용.
token keyword.fn = 'fn'   // 'fn' → keyword.fn
token ident      = /[a-zA-Z_][a-zA-Z0-9_]*/
token lit.number = /[0-9]+(\.[0-9]+)?/
문법02b · 규칙 = 모양이자 표시 문법
레이블은 접근자, 리스트는 sep(). 식은 praat — @는 식(simple) 자리 표시자, 숫자는 토큰 사이 결합력. 배치가 연산자 모양(전위·중위·후위·혼합)을 그린다.
FnDecl = 'fn' name:ident params:sep(Param, ',') …

Expr = praat {
  simple = Lit | Ident | ParenExpr
  operators {
    '+' | '-' | '!' @100,
    @89 '**' @90,
    @80 '*' | '/' @79,
    @70 '+' | '-' @69,
    @40 '?' @0 ':' @39,   // a ? b : c
  }
}
03-elab.langue

정제 — from A to B 재작성 · between A 관계

*.elab.langue는 from A to B 블록으로 재작성 규칙을 선언한다. 규칙은 패턴 ==> 구성이고, 구성 안의 … to MIR가 하위 트리의 재귀 정제다. 같은 from/to 블록은 여러 정의·여러 파일에 걸쳐 병합된다. 엄격히 감소하는 재귀만 허용(종료 보장), 충돌하는 규칙은 불허(에러 — 규칙 순서·우선순위 없음). 같은 언어 위에서는 between A 블록으로 관계를 정의한다 — === 등식이 e-graph 등식 포화(05c)로 돈다. $x는 메타변수, subst 택틱은 내장: $e[$b := $a].

*.elab.languefrom · to · ==>
from Lumo to MIR {
  FnDecl { ... } ==> Lambda { ..., body: Lumo::FnDecl { ... } to MIR }
  ...
}

// 여러 정의·여러 파일에 걸쳐 병합
from Lumo to MIR { ... }
between A같은 언어 · === · e-graph
between A {
  // 항등 함수 적용은 인자와 같다
  Apply { fn: Lambda { param: $f, body: $f }, arg: $e } === $e
}

between A {
  // subst 택틱 내장 — 베타 축약
  Apply { fn: Lambda { param: $b, body: $e }, arg: $a } === $e[$b := $a]
}

스코프는 1급 개념이 아니다: .scope.langue 종류도, 별도 스코프 엔진도 없다 — 정제가 스코프를 시뮬레이트한다. 그리고 재귀는 fix로만 실현한다: letrec 코어 형식은 없다. 상호 재귀 정의 그룹(SCC)은 fix (λ(f, g). (body_f, body_g))처럼 fix 원시 하나로 로워링하고, 순환 없는 정의는 그냥 let이 된다. (리터럴 Y 콤비네이터가 아닌 fix 원시 — Y는 Fω에서 타입이 안 붙는다.)

04-type.langue

타입 — 지금 정의하는 중

타입 AST 자체가 *.syn.langue로 정의된다. 타입은 표시 문법(presentation)을 가지므로 하나의 하위 언어(sub-language)다. 그래서 TypeV·TypeC(CBPV 값/계산 타입)를 문법 통합 AST로 자연스럽게 지원한다. 그리고 context는 이름 붙은 멀티맵이다 — 이론적으로는 튜플 집합.

infer와 check는 정의 가능한 판단이다 — λProlog식 관계 언어. 화살표(-> / <-)는 두 매개변수 사이의 구분자 표기일 뿐 — 둘 다 그냥 매개변수다. 관계 언어라서 대입은 유도의 아래에서 일어나 위로 전파되고, 그래서 타입 매개변수는 사실상 inout이다. with는 문맥을 붙인다 — 여러 개일 수 있다. 규칙은 head := body이고, =는 단일화, 괄호친 판단 호출이 골(goal)이다. _V/_C 같은 접미사는 엔진에 아무 의미가 없다 — 판단 이름은 그냥 이름, 함수 명명 규칙 같은 것 (infer_ε, infer_wtf 전부 유효). 문맥 쓰기는 골에 지역 확장 문맥을 넘기는 것: with Γ+{a: b}. 판단 재귀도 elab과 같은 규율로 엄격 감소만 허용, 한 골에는 정확히 하나의 규칙만 성공해야 한다(둘 이상 성공 = 에러). 구현은 λProlog를 참조한다.

내장 택틱은 최소로 시작해 나중에 확장한다 — 지금은 subst와 hash. capability row는 전용 자료형이 없다: 키가 해시면 맵이 곧 집합이라, row는 기존 멀티맵 기계 위에 탄다 (hash가 내장). 진단은 지금 설계하지 않는다 — 실패하면 일반 메시지로 bail. 진입점은 매니페스트: Lumo.langue가 Lumo.syn.langue·Lumo.elab.langue·LIR.type.langue를 파이프로 잇는다.

context멀티맵 · 튜플 집합
context Γ = [Ident: TypeV]
judgmentλProlog식 관계 · -> 산출 · <- 검사
infer_C LIR -> TypeC with Γ
check_C LIR <- TypeC with Γ

// 규칙: head := body
infer_V TypeAssignment { expr: $e, ty: $t } -> $inferred
  := $inferred = (check_V $e <- $t)

// 문맥 접근: Γ.$name
infer_V Ident { name: $name } -> $return := $return = Γ.$name

// 문맥 쓰기: 골에 확장 문맥을 넘긴다
check_C a b with Γ+{a: b}

단계별 딕테이션으로 정의 중 — 이어지는 결정을 따라간다. 타입 플러그인 같은 건 없다 — 타입 시스템은 정의가 선언한 판단 그 자체다. 판단은 진짜 유도 트리를 만드는 범용 관계 엔진(05d) 위에서 돌고, Lumo v1의 판단이 Fω + spine-local 양방향 + capability row를 구현한다. 진단 템플릿은 규칙 옆, DSL 안에 산다.

 05d

05a

salsa식 증분 질의, 첫날부터

모든 파생 산출물은 입력에 대한 메모이즈된 질의다. 편집이 더럽힌 것만 다시 계산한다. cat/병합/DCE가 만드는 정의는 리비전당 하나의 불변 값 — 메모이제이션이 원하는 바로 그 형태다. 두 층이 같은 질의 런타임 위에 선다.

정의 층 (langc) · parse(file)→ merged_definition→ rule_tables(kind)→ 생성 코드
컴파일 층 (생성된 컴파일러) · cst(file)→ mir(file)→ infer(node)

.type.langue 파일 하나를 고치면 타입 테이블만 재파생된다. 후보 런타임: salsa 크레이트, 혹은 관계 엔진과 충돌하면 목적 제작.

05b · langue 1의 혈통

ungrammar식 표기 — 모양을 쓰면, 알고리즘은 유도된다

.langue 표기는 트리의 모양을 기술하지, 파싱 알고리즘을 기술하지 않는다. 레이블은 접근자가 되고, 대안은 노드 종류가 되고, 파서는 모양(+ 우선순위 주석)에서 유도된다. 파이프라인의 모든 단계(Lumo, MIR, LIR, JS)는 각자 문법으로 선언되는 개별 언어이고, 따라서 자기 표시 문법을 가진다. 언어마다 파서와 프리티 프린터가 유도되어 모든 단계가 텍스트로 왕복한다. 이 철학이 문법 너머까지 간다: elab 규칙·타입 규칙 전부가 엔진이 해석하는 모양-우선·알고리즘-부재 선언이다.

// 무엇을 쓰는가: 트리의 모양 = 곧 그 트리의 표시 문법
FnDecl = 'fn' name:Ident params:sep(Param, ',') …
// 무엇을 쓰지 않는가: peek() / expect() / 재귀 하강의 순서 / print 함수
05c

e-graph 정제 — 최적화는 등식 포화로

언어 간 정제는 구문 지향, 같은 언어 최적화는 e-graph 등식 포화 + 비용 추출 — 규칙 순서가 무의미하다. 엔진은 egglog. 같은 언어 규칙은 between 블록으로 선언(03). 비용 모델은 널리 쓰이는 모델을 리서치해 채택한다.

05d

관계형 타입 엔진 — 판단이 곧 타입 시스템

관계 엔진

λProlog식 판단 언어(04)의 실행기. 골을 풀고 단일화하며 진짜 유도 트리를 만든다. 엔진은 Lumo를 모른다.

타입 플러그인은 없다

타입 시스템은 정의가 선언한 판단 그 자체. Lumo v1의 판단이 Fω + spine-local 양방향 + capability row를 구현한다.

유도가 곧 산출물

실패한 전제 → 진단 템플릿. 성공한 유도 → "왜 이 타입인가" 설명과 LSP 호버. 모든 유도는 salsa 질의라 증분 재검사가 공짜로 따라온다.

Γ ⊢ f ⇒ Fn(π, ρ | ε) Γ ⊢ a ⇐ π Γ ⊢ f(a) ⇒ ρ | ε
else error "cannot call a non-function of type {0}" at f
else error "expected {param}, found {0}" at a

전제 위에 마우스를 올리면 그 전제가 실패했을 때의 진단이 표시됩니다 — 진단 템플릿은 규칙 옆, DSL 안에 산다

06-exec.langue

실행 모델 — 세 종류 모두 코드 생성

syn·elab·type 전부 Rust 코드로 생성한다 — 해석되는 규칙 테이블은 없다. crates/langc 하나가 라이브러리(컴파일러에 정의를 탑재) + CLI (langc gen, langc check)를 겸한다. 워크플로는 하나 — 수정, langc gen, 커밋.

syn

선언된 언어마다 Rust 소스
  • 토큰 DFA, SyntaxKind, 트리
  • 타입이 붙은 AST 접근자
  • 파서 (praat 블록 + extern 복구 훅)
  • 프리티 프린터 — 텍스트 왕복

elab

from/to · between → Rust
  • from/to 재작성 → 생성된 Rust
  • between 관계 → egglog(05c) 위에서 도는 생성 코드

type

판단 → Rust
  • 판단 규칙 + 진단 템플릿 → 관계 엔진(05d) 코드
07-open.langue

열려 있는 것 — 다음 설계 대상

잠긴 결정은 이 페이지에 없다 — design/decisions/에 결정당 파일 하나(27개). 여기는 아직 열려 있는 것과 다음 논의 후보만.

다음 논의 후보

  1. 비용 모델 리서치(액션) — 널리 쓰이는 모델을 조사해 채택안을 보고: egg/egglog의 생성자별 비용 + 최소 총비용 추출(:cost 주석), extraction-gym 계열(greedy vs DAG-aware/ILP).
  2. 같은 종류 병합에서 규칙 우선순위/오버라이드 — 두 파일이 같은 노드에 규칙을 내면 에러인가, 명시적 override인가?
  3. stdlib의 범위 — 도우미 콤비네이터·표준 토큰 외에 무엇까지? (진단 서식 도우미 등)
  4. 정제의 스코프 시뮬레이션 방식 — 이름 해소·use/모듈·캡 핸들러의 동적 스코프를 어떤 재작성으로 담는가?
  5. 진단 템플릿의 다국어/수준(note, help) 지원 여부.
  6. langue 프로젝트 자체의 테스트 형식 — golden 픽스처를 어떤 모양으로 쓸지. 픽스처 소스 아이디어: tree-sitter와 legacy 프로젝트(legacy/crates/compiler/tests/fixtures).
08-milestones.langue

마일스톤

각 단계에서 langc check와 golden 테스트를 초록으로 유지. golden 픽스처가 각 단계의 계약이다.
